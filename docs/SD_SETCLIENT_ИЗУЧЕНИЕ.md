# Смена агента у точки через API SalesDoc: изучение (только анализ)

> Статус: **изучение, ничего не реализовано**. Портал остаётся read-only к
> SalesDoc (только `get*`). Документ фиксирует, что метод существует, чего
> он стоит и какие риски надо снять ПЕРЕД тем, как что-то писать.
> Источник: официальная документация API V2
> (github.com/Clever91/salesdoc-api-doc), раздел 10.17.

## Метод есть: setClient (10.17)

«Создаёт или обновляет клиентов с привязкой агентов и расписанием
посещений». То есть смена агента у точки технически возможна — и это ровно
тот же объект, который мы читаем через `getClient`.

Пример из документации:

```json
{
  "method": "setClient",
  "auth": { "userId": "d0_1", "token": "..." },
  "data": { "client": [ {
      "code_1C": "000000100",
      "shortName": "Магазин Звезда",
      "clientCategory": { "code_1C": "000000001" },
      "agent": [ { "code_1C": "000000003", "visitDays": [1, 3, 5] } ]
  } ] }
}
```

| Поле | Обяз. | Комментарий |
|---|:---:|---|
| `code_1C` / `SD_id` | ✅ | идентификатор точки |
| `shortName` | ✅ | краткое наименование |
| `clientCategory` | ✅ | категория — **обязательна даже при смене агента** |
| `agent[].code_1C` | ❌ | кому закрепляем |
| `agent[].visitDays` | ❌ | дни маршрута, 1=Пн … 7=Вс |
| `deleteVisits` | ❌ | `"true"` удаляет предыдущие визиты |
| `firmName`, `address`, `tel`, `lat`, `lon`, `active` | ❌ | прочие поля карточки |

Round-trip сходится: `getClient` отдаёт `agents:[{id, code, days}]` —
запись принимает `agent:[{code_1C, visitDays}]`. Значит текущее состояние
читается и воспроизводится точно.

## Главный риск: неизвестна семантика частичного обновления

**Документация не описывает, что происходит с полями, которые не переданы**
— затираются или сохраняются. Для метода с названием «создаёт или
обновляет» это ключевой вопрос: если незаполненные поля обнуляются, запрос
«поменяй агента» может стереть адрес, телефон, координаты, признак
кредита. Отсюда правило: **передавать полную карточку** — сначала
`getClient`, потом обратно всё, что он вернул, с изменённым только блоком
`agent`. Проверять на одной тестовой точке.

Второй непроверенный момент — `deleteVisits`: неясно, удаляет ли он
историю визитов или только плановое расписание. Не передавать, пока не
выяснено у поддержки.

## Технические ограничения (из 01-general.md)

- Единый эндпоинт `/api/v2`, только POST, всегда JSON.
- **Пакет — максимум 250 записей** в одном SET-запросе, иначе ошибка 407.
  Массовая переброска точек уволенного агента бьётся на пачки.
- **403 — «доступ к методу запрещён, список запрещённых методов
  настраивается на сервере»**: не факт, что нашему аккаунту вообще
  разрешены set-методы. Проверяется одним безопасным вызовом.
- Rate limits именные: `setStock` 5/5 сек, `setCurrentBalance` 3/5 мин;
  для `setClient` лимит не указан — считать, что он есть, и слать пачками
  с паузами. Ошибка 429 = «подождать».
- Токен один на устройство: повторный `login` инвалидирует старый. Портал
  и человек, работающий в веб-интерфейсе SD под тем же пользователем,
  могут выбивать друг друга — для записи нужен **отдельный служебный
  пользователь**.

## Побочная находка (важно для текущего кода)

Документация: **`getStoreLog` доступен только с 20:00 до 07:00** и имеет
лимит 5 запросов за 5 секунд. Это объясняет наши HTTP 429 и «пустой
журнал» при дневных прогонах — синк журнала склада надо ставить на ночь,
а днём показывать последний сохранённый результат. Проверить и учесть
отдельно от темы setClient.

## Если однажды делать (порядок, не реализовано)

1. Спросить поддержку SalesDoc: разрешены ли set-методы нашему аккаунту;
   семантика частичного обновления; поведение `deleteVisits`; лимит
   частоты для `setClient`.
2. Завести отдельного служебного пользователя API для записи (свой токен).
3. Реализовать **сухой прогон**: портал строит список изменений
   (точка — было — стало) и показывает на экране; никакой записи.
4. Запись — только по кнопке подтверждения на подтверждённый список,
   полными карточками (get → изменить агента → set), пачками ≤250,
   с журналом изменений и возможностью отката (обратный setClient).
5. Отдельная роль/право на портале; по умолчанию выключено.

Пока пункт 1 не пройден — режим остаётся read-only.
