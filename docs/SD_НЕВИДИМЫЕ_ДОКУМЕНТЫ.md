# Невидимые для API документы SalesDoc: разбор на клиенте y8_96

> Повод: карточка «ИП Осмонов Аманбек (Аманбек Ошский) (y8_96)» — в 1С
> 7 реализаций, SalesDoc отдаёт 1. Раньше это объяснялось версией
> «документы деактивированных агентов не приходят в API». Ниже — проверка
> этой версии по данным, и она **подтверждается только частично**.

## Что доказано арифметикой

Баланс клиента в SalesDoc — **94 584 KGS**. Если сложить операции, которые
API по нему отдал, получается **−889 576 KGS**. Разница — **984 160 KGS**.

Теперь 1С: реализации без пары в SalesDoc —
67 456 + 21 080 + 6 048 + 843 200 + 35 836 + 10 540 = **984 160 KGS**,
ровно до сома.

Сходится и остальное:

| Величина | 1С | SalesDoc (API) |
|---|---:|---:|
| Реализации | 1 068 480 · 7 | 84 320 · 1 |
| Оплаты | 938 060 · 8 | 853 740 · 7 |
| Возвраты | 120 156 · 2 | 120 156 · 2 |
| Сальдо | 10 264 | 94 584 (заявленный) |

Разница по оплатам — 84 320: банковская оплата от 07.08.2026, которая в 1С
есть, а в SalesDoc ещё не проведена. И 10 264 + 84 320 = 94 584 — сальдо
SalesDoc сходится с 1С копейка в копейку.

**Вывод: SalesDoc внутри себя знает все семь реализаций** — иначе его
собственный баланс не совпал бы с 1С. Через API он отдаёт одну. Это не
расхождение учёта, а **невидимость документов для API**.

Дополнительное подтверждение: getOrderDefect отдаёт по клиенту 2 возврата,
и один из них (35 836 от 17.06.2025) относится к реализации 27.01.2025 на ту
же сумму — то есть возврат **виден**, а его родительская реализация — нет.

## Зеркало ни при чём

«Всего просмотрено в SalesDoc: 1153 заказа · 2028 операций» против «всего
строк в зеркале: 1153 · 2027». Живой запрос мимо зеркала возвращает столько
же. Наша синхронизация переносит всё, что API отдаёт: проблема на стороне
выдачи SalesDoc, не в портале.

## Версия «деактивированные агенты»: что за и что против

**За:** выгрузка Чингиза из веб-интерфейса содержала 70 заявок, которых API
не отдаёт; 65 из них — агенты Айткулуев (OSDO) и Усупеков (BC 2), которых
среди активных нет. Совпадает и арифметика: 1153 (API) + 70 = 1223 — число
заказов, которое мы видели в более раннем зонде.

**Против:** невидимые реализации этого клиента датированы с 29.11.2024 по
**06.02.2026**, а заявки Чингиза — только ноябрь 2024 — январь 2025. Если бы
агентов деактивировали в начале 2025, документов 2026 года у них быть не
могло. Значит одной деактивацией всё не объясняется.

## Другие кандидаты (ранжированы)

1. **Ловушка фильтра статусов.** Мы просим `status: [1,2,3,4,5]` —
   Новый/Отправлен/Доставлен/Закрыт/Отменён. Если в SalesDoc есть статус вне
   этого диапазона (0, 6+, черновик, удалён), документы молча выпадают. У
   `getOrderDefect` ровно такая ловушка уже ловилась: без явного списка
   сервер отдаёт только статус 1.
2. **Другая учётная запись / филиал.** В 1С у регистра
   `ИдентификаторыSalesDoctor` есть поле **УчётнаяЗапись** — значит записей
   может быть несколько. В API есть необязательный блок `filial`. Если часть
   документов заведена в другом филиале/аккаунте, наш токен их не увидит.
   Косвенно: невидимые заявки Чингиза проходили через склад
   **«Основной склад(типовой )»**, а видимая реализация — через «Основной
   склад Хайджин Бишкек». Клиент — ошский, агент — с суффиксом **OSDO**.
3. **Видимость по пользователю.** Токен принадлежит конкретному
   пользователю SalesDoc; выдача могла ограничиваться его правами
   (территория, команда супервайзера), а не активностью агента.
4. **Деактивированные агенты** — см. выше, объясняет часть периода.

## Как проверить (решающие опыты)

Все — только чтение, никаких `set*`.

1. **Запросить заведомо невидимый документ по номеру.** Из выгрузки Чингиза
   известны номера (26–237, например №161 от 20.12.2024, точка «Конт 1 Ала
   Арча Гульмира»). Если `getOrder` с фильтром по этому номеру/ИД вернёт
   документ — проблема в фильтрах запроса. Если «не найдено» — в видимости.
2. **Перебор статусов.** Тот же период и клиент, но `status` перебором
   0…9 по одному, и вовсе без ключа `status`. Покажет ловушку статуса.
3. **Через возврат.** У возврата z6_1442 (35 836) взять ссылку на
   родительский заказ — получим SD-идентификатор скрытой реализации и
   запросим её напрямую.
4. **Журнал склада.** `getStoreLog` отдаёт документы **по складу**,
   независимо от агента. Прогнать по складу «типовой» на даты пропавших
   документов. (Помнить: журнал доступен только с 20:00 до 07:00.)
5. **Блок `filial`** и вопрос в поддержку SalesDoc: сколько учётных записей
   у компании и ограничивает ли выдачу getOrder активность агента.

## Что это меняет для портала

Пока причина не найдена, **нельзя утверждать «в SalesDoc нет»** — корректная
формулировка «API SalesDoc не отдаёт». Плюс нужен постоянный контроль:
сверять заявленный баланс клиента с суммой его операций (как в этой
карточке) — расхождение и есть индикатор невидимых документов. По этому
клиенту оно составило 984 160 KGS.

# Результаты зонда (19.08.2026) и проверка версии про агентов

Зонд отработал по y8_96, окно 21.08.2025 – 20.09.2026, 16 запросов, 174 с.

## Три версии закрыты

| Версия | Результат |
|---|---|
| Фильтр статусов | **опровергнута**: вне 1–5 пусто (0, 4, 6–9 дают ноль), у клиента при любом статусе одна реализация на 84 320. Побочно: **без ключа `status` сервер отдаёт всего 2 записи** вместо 762 — по умолчанию он прячет почти всё, наш явный список правилен |
| Филиал | **опровергнута**: с филиалом и без — 762 / 1 строка клиента, одинаково (филиал не настроен) |
| Поиск по номеру | **не работает**: все четыре формы (`filter.number`, `filter.docNumber`, без периода, `params.number`) вернули по 2 записи — ровно столько же, сколько запрос без фильтров. Ключ `number` сервер игнорирует |
| Ссылка на родителя в возврате | **пути нет**: в сырой записи `getOrderDefect` есть клиент, агент, склад, тип цены, товар — ссылки на родительскую реализацию **нет вовсе** |

## Ключ `agent` тоже игнорируется

Перебор по агентам остановился после первого: запрос с фильтром по агенту
вернул ровно ту же выдачу, что и без него. **Проверить версию про
деактивированных агентов через API невозможно** — и обхода «тянуть заказы
поагентно» тоже нет.

## Что показали данные 1С по этому клиенту

Семь реализаций 1С, одна видна в SalesDoc:

| Дата | Сумма | Ответственный | Видна в SD |
|---|---:|---|---|
| 29.11.2024 | 10 540 | — не заполнен | нет |
| 27.01.2025 | 35 836 | — не заполнен | нет |
| 01.02.2025 | 843 200 | Айткулуев Сыдык | нет |
| 13.05.2025 | 6 048 | — не заполнен | нет |
| 13.12.2025 | 21 080 | Айткулуев Сыдык | нет |
| 06.02.2026 | 67 456 | Айткулуев Сыдык | нет |
| **06.08.2026** | **84 320** | **Смаилова Айдай** | **да** |

На этом клиенте версия ложится идеально: единственный видимый документ — у
действующего агента, все шесть скрытых — у Айткулуева либо вовсе без
ответственного.

**Но в масштабе она не сходится.** По всему файлу реализаций Хайджин:

- всего 1 519 документов, в зеркале SalesDoc за три года — 1 221 заказ
  (и это по обеим фирмам), то есть не видно минимум **298**;
- у Айткулуева во всей базе **7 документов**, у Усупекова — **4**.
  Одиннадцать документов не могут объяснить разрыв в три сотни;
- **640 документов вообще без ответственного**, и большинство из них
  видно — значит «пустой ответственный → невидим» тоже неверно.

Отдельно: мой прежний контраргумент («скрытые документы датированы февралём
2026, а агентов деактивировали в начале 2025») **снимается** — документ от
06.02.2026 как раз Айткулуева, значит он работал ещё в 2026-м и отключён
позже. Дата деактивации мной не проверялась, вывод был построен на догадке.

## Что это значит

Версия про деактивированных агентов **не опровергнута и не подтверждена**:
через API её проверить нечем, на одном клиенте она совпадает, на всей базе
не масштабируется. И важная оговорка: «Ответственный» в 1С — это
пользователь 1С, а не агент SalesDoc. Правильное поле — `SD_Агент`, которого
в выгрузках пока нет (см. `1С_РЕД17_ЧТО_НУЖНО.md`).

## Осталось два хода

1. **`getStoreLog`** — журнал по складу, агента не спрашивает вовсе.
   Единственный независимый канал. Работает только с 20:00 до 07:00.
   Склад скрытых документов — `d0_5` «Основной склад Хайджин».
2. **Обращение в поддержку SalesDoc** с воспроизводимым отчётом: клиент
   `y8_96`, баланс сходится с 1С до сома, `getOrder` при любых параметрах
   отдаёт 1 документ из 7, разрыв 984 160 сом, ключи `number` и `agent`
   в фильтре игнорируются.
